# Why the phone profile misses J12 — issue #1473

Completed 2026-11-20 07:57 JST. Canonical report: `/Volumes/KIOXIA/scratch/diag-1473/diag.md`. Review copy: this file. Product code is unchanged.

## Conclusion

The gap is CPU-bound: throttling magnifies expensive camera collision raycasts. Phone geometry alone runs fast on the M2 Pro GPU. However, 4× is only moderately too severe for the selected mid-tier CPU reference; the evidence does **not** support dismissing the phone failure as mostly an invalid throttle setting.

Full-walk median FPS is **117.65 at 1×, 42.02 at 2×, and 20.28 at 4×**. The original 17.57 fps is not exactly reproduced, but the 4× run still misses 30 fps. The separate profiled frame spends **38.3 of 50.1 ms in camera placement**, with **5.96 ms GPU time**. Native instanced-mesh raycasting is the dominant sampled stack.

Use **3.03× CPU throttle on this host/browser** for the DevTools Pixel 5-like mid-tier reference, retaining the existing phone geometry. This is a recommendation only; the measurement script has not been changed. FPS at 3.03× was not measured: interpolation of median frame intervals between 2× and 4× suggests approximately **27 fps**, so recalibration alone is unlikely to secure J12. This interpolation is an estimate, not an acceptance result. No real phone was measured; J12 remains open.

The code explains this stack: [castAll](https://github.com/nurockplayer/gteki/blob/10711276f27ebebd93b09f688e27af10eff769d2/apps/web/src/explorer/raycast.ts#L93) tests each camera target and sorts all accepted hits; [raycastObject](https://github.com/nurockplayer/gteki/blob/10711276f27ebebd93b09f688e27af10eff769d2/apps/web/src/explorer/meshBvh.ts#L133) delegates custom/instanced meshes to their native raycast. The existing BVH accelerates ordinary static meshes, not that native instanced path. Three 0.186.1's `InstancedMesh.raycast` tests the whole batch sphere, then loops every instance and calls ordinary mesh raycast. Camera boom placement can issue several candidate rays and another ray for the final damped pose ([placeCamera](https://github.com/nurockplayer/gteki/blob/10711276f27ebebd93b09f688e27af10eff769d2/apps/web/src/explorer/explorer.ts#L3735)). The sampled instanced path therefore bypasses the existing triangle-tree acceleration. Specific batch names/instance IDs were not captured; no claim is made that a particular asset alone causes the cost.

## What mid-range means and which throttle to use

[Chrome DevTools recommends calibrating CPU presets to the host](https://developer.chrome.com/docs/devtools/settings/throttling). Its [calibration source](https://github.com/ChromeDevTools/devtools-frontend/blob/main/front_end/panels/mobile_throttling/CalibrationController.ts) explicitly uses a **Pixel 5-like mid-tier reference with Lighthouse BenchmarkIndex 1000**. This is a concrete browser CPU target, not a universal definition of every phone sold as mid-range in 2026.

The scratch runner extracts the same string-allocation/array-copy benchmark, warms V8, runs 250 ms iterations, and reproduces the low-tier-then-mid-tier bisection with a ±10-point stopping tolerance. Calibration completed **2026-11-20 07:55:15 JST**:

| Setting | CPU throttle | Benchmark score |
|---|---:|---:|
| Host baseline | 1× | 3129 |
| Calibrated low-tier reference | 11.48× | 256.5 (target 264) |
| Calibrated mid-tier reference | **3.03×** | **1009 (target 1000)** |

Recommendation: **3.03× for a Pixel 5-like CPU proxy on this M2 Pro and Brave version; keep 1× as the phone-layout control and 4× as a conservative stress reading.** 4× is 32% more slowdown than the calibrated 3.03× setting. Recalibrate when the host/browser changes. A faster contemporary phone may warrant less throttling, but that requires a defined device/reference rather than choosing 2× because it passes.

Calibration measures CPU/memory JavaScript performance only. It leaves the M2 Pro GPU, desktop memory/thermal behavior, and Chromium platform in place. Neither the 1× result nor this calibration proves real-phone J12 performance. At unchanged CPU work, linearly interpolating the 2×/4× median intervals (23.8 / 49.3 ms) gives 36.93 ms, approximately 27.1 fps at 3.03×; rAF quantization and pose mix limit this prediction.

## Most promising fixes — estimates, not implemented

1. **Accelerate the instanced camera-collision path.** Add per-instance spatial rejection and shared geometry BVH traversal to the currently native path, preserving transforms, material sides, portal filtering, face/instance identity, and moving-instance behavior. This directly addresses the dominant sampled stack. **Expected gain:** target a 50–75% reduction in the 38.3 ms camera stage; with the other 11.8 ms unchanged, the profiled 4× frame model falls from 50.1 ms to 31.0–21.4 ms (**about 32–47 fps, 1.6–2.3×**). This is an engineering target and an optimistic bound if other camera work stays significant, not a measured speedup or a whole-walk guarantee. **Visual cost:** none intended; the same collisions and camera poses should result. Costs are acceleration-structure memory/build/update work.
2. **Broad-phase camera targets before repeated boom rays.** Spatially shortlist targets against the entire candidate-boom envelope once per frame, and reuse that conservative shortlist across the solver and final damping check. Keep all existing candidate checks and exact hit semantics; do not remove ceiling/body clearance checks to buy FPS. **Expected gain:** a 20–40% reduction in the measured camera stage would save 7.7–15.3 ms, giving approximately **24–29 fps at 4×, 1.2–1.4×** from the same 50.1 ms local frame model. Actual gain depends on how much irrelevant geometry survives current batch spheres, and it overlaps with fix 1; do not add the estimates. **Visual cost:** none intended with a conservative shortlist. This is the smaller alternative if instanced traversal is too large a first change. Lowering DPR or disabling more visual features is a weaker first move here: the existing phone GPU work is near 6 ms, while camera CPU alone is 38 ms.
