### A.2 CRS findings by file group

Structure of the ZIP (25 members): `com-map` and `com-entity` documents, 11 `geojson-level-geom-*` files, 11 `path-level-geom-*` files, `v5_nav.json`.

| File group | `crs` member | Verdict | Basis |
| --- | --- | --- | --- |
| `geojson-level-geom-*` (11 levels; 15,556 features in all, 90,784 coordinate positions) | absent in all 11 | **VERIFIED: WGS84 longitude/latitude in degrees** | The specification states the rule for exactly this file group. Quote (once): 「CRS が存在しない場合、データは WGS84 緯度経度座標で提供されます」 (p8). It repeats that for the HERE Venues data the lat/lon form omits the CRS entry (p8-p9), and Q&A 1 says coordinates are degrees (p13). |
| same, axis order | n/a | INFERRED: x = longitude, y = latitude | Standard GeoJSON order; every file's bbox is x about 139.70, y about 35.69 (see `poi-rights-s10-s03-related.md`, "Native XY bbox"). No file has a third (Z) coordinate. |
| same, datum realisation | n/a | **UNKNOWN** | The text says "WGS84" only. It names no realisation, epoch or relation to JGD2011 (EPSG:6668). |
| `com-map.geojson` `location` point | absent | INFERRED (same rule as the geometry files) | A two-number point in the same degree range; the specification rule is stated for the level geometry files, not for this field. |
| `path-level-geom-*` (11) | **explicit `"crs": null`** | **UNKNOWN as native coordinates** | The specification says an explicit null means coordinates cannot be inferred (p8). Per p7 these use the drawing's local coordinates; the specification does not define the local frame beyond `ref_frame`. |
| `path-level-geom-*` via `ref_frame.transform` | n/a | INFERRED relation, see A.3 | The array order of `transform` is not documented for `ref_frame` (p6 says only "local to lat/lon"). |
| `v5_nav.json` (`mx`, `my`) | absent (not a GeoJSON) | UNKNOWN native frame | Spec p16-17 calls it "Mercator" without ellipsoid, origin or scale. Lane B shows it must not be fed to a plain EPSG:3857 inverse and used the drawing transform instead. |
| `com-entity.geojson` | absent | no coordinates | 423 entities carry no coordinate member; 414 reference a geometry id that is not a level-feature `id`. Placement goes through the feature `entities` list instead (C.2). |

The register's `UNKNOWN` therefore stays correct for (a) the datum realisation, (b) the `path-level` and nav native frames. It is too conservative for the 11 `geojson-level-geom` files, where the first-party statement exists. The repository's existing rule (an absent `crs` is only the RFC 7946 assumption, an explicit null is UNKNOWN) is consistent with this; the new fact is that the S03 specification itself says so.

### A.3 Independent consistency evidence (INFERRED, not a CRS proof)

1. **Affine check (this run).** For the B1F level, 1,083 features exist in both `geojson-level-geom-B1F` and `path-level-geom-B1F` with a `location` point (1,246 ids are common; the Path file has 2 more). Applying the drawing's six-number `ref_frame.transform` (lon = a0*x + a2*y + a4, lat = a1*x + a3*y + a5, the same layout the specification documents for the nav drawing transform) to the Path-local point reproduces the GeoJSON point with a median error of 0.075 m, p90 0.087 m, maximum 0.117 m, which is what 7-decimal degree rounding allows. So the two files share one frame and the transform order is right. It says nothing about which datum that frame is.
2. **Horizontal agreement with an independent network (Lane B, #61).** The navigation layer transformed to lon/lat and treated as JGD2011/GRS80 against the checked-in E27 network (EPSG:6668): 15 reciprocal pairs within 5 m, median 1.854 m, p90 3.367 m, maximum 3.418 m, no fitted correction. That bounds the combined error to metres; WGS84 realisations and JGD2011 differ far less than that, so this cannot tell them apart. Lane B explicitly did not establish a WGS84-to-JGD2011 correction.
3. **Place.** `station_relevance` in the generated research doc: 108 of the 525 level-file comparisons intersect the Shinjuku PLATEAU/Hokonavi bboxes, 0 intersect Ikebukuro. That is a sanity check only.

**Verdict for the register (proposal):** S03 `geojson-level-geom-*`: `crs_basis = "WGS84 lon/lat, declared by S03 specification p8"`, status VERIFIED for the group, `datum_realisation = UNKNOWN`, uncertainty "metre scale, INFERRED from #61". Path and nav: unchanged UNKNOWN, with the inferred affine link recorded as a derivation, not a declaration.

The column carries no stated reference (ground, rail level, TP or other). Reading its dataset description is a next action; until then it is UNKNOWN what the number is measured from. It is per station, not per S03 level.

### A.5 What a GIS importer would need (proposal only)

1. **Per-file CRS record, three states.** `DECLARED_BY_SPEC_DEFAULT` for the 11 level-geometry files (cite the specification SHA-256 and page), `EXPLICIT_NULL` for the 11 Path files, `UNDEFINED_FRAME` for nav. Never write EPSG:6668 or EPSG:4326 as a declared value; emit CRS84-style lon/lat with `datum_realisation: UNKNOWN` and a flag that any use as JGD2011 is an assumption good to metres.
2. **Prefer the level-geometry files for placement.** They are the only group with a first-party CRS statement and carry the same features as the Path files (B1F: 1,246 shared ids). Treat Path and nav as drawing and topology, placed only through a recorded derivation.
3. **Derivation record for Path/nav.** Store the `ref_frame` transform, the array-order assumption, the residual test (A.3 item 1) and, for nav, the drawing transform plus Lane B's method. Fail the import if the residual test exceeds a set bound (for example 0.25 m on a re-run).
4. **Levels as opaque.** Persist `level_label` (string, opaque), `level_rank` (the integer `zlevel`, ordering only), `level_kind` and `height_m: UNKNOWN`. Do not compute a height from rank. Mapping S03 levels to the Shinjuku station frame (street = z 0) must be an explicit, reviewed lookup table per station, owned by Lane B, with a `basis` column; absent entries mean UNKNOWN, not nearest.
5. **Checks to run on every import.** Axis-order test against the station bbox; bbox containment; absent-versus-null `crs` handled differently (the repo already tests this); level count and rank-gap report; and a regression residual against the E27 network (Lane B's 15-pair statistic as the baseline).
6. **Outputs.** Every record `routable: false`, `verification: UNVERIFIED`, publish gate HOLD; credit string per the Owner's answers (S03 wording and change notice).

### A.6 Still UNKNOWN in section A

## B. Replacement sources for the refused Shinjuku POI layers

### B.1 Method and verdict rules

Searched: Tokyo open-data catalogue (CKAN, `package_search` and `package_show`), Shinjuku ward datasets, 国土数値情報 product pages and terms, GSI pages. Access date 2026-10-22. Only landing pages and catalogue metadata were used; for four small municipal CSVs (items 2, 5, 8, 9) the first (header) row was read in a transient fetch to learn whether coordinate columns exist, and **no row value was kept**. The Tokyo shelter CSV was too large to fetch (item 4). The 106-row Toei station table (item 12) was downloaded once to the session scratchpad, outside the repo, to read its remark columns; only its schema and meaning are recorded here.

**Licence level matters.** No Tokyo CKAN resource below has its own `license` field (all are empty); the CC BY 4.0 statement is on the dataset (package). That is the same shape as S03, which the Owner accepted for S03 in Q3 only. KSJ product pages state the licence for the whole product, whose download table is the resource. So the verdict codes mean:

- **CANDIDATE**: CC BY 4.0 stated at dataset or product level by the data owner, coordinates present in the data, edition dated 2024 or later. Strictly, none states it on a separate resource record; using one still needs the Owner to extend the Q3 reasoning (Owner question B1).
- **CONDITIONAL**: licence is explicit but coordinates are unconfirmed, the data is old or tiny, a third-party or approval notice applies, or terms point elsewhere.
- **NOT_USABLE**: non-commercial, no landmark content confirmed, or terms prevent redistribution of extracted data.

### C.3 Rules for any placement

- A placed point comes from S03 geometry, carries S03's CRS status (A.2), and is labelled `placement_source: S03_phone_match` (or `S03_name_hint`), `verification: UNVERIFIED`. The S10 record supplies only its own plain fields.
- The match key, the S03 feature id and the S03 level label are stored; no S10 free text is converted into a level, an entrance or a gate side.
- A containment-only name relation is never auto-accepted; it is a review item with a hash of the S03 feature id.
- If the S03 and S10 source are given different credits, both credits and the change notice must travel with the combined record (Owner credit wording).

### C.4 Stays UNKNOWN

- The coordinate, level, entrance and fare-side of every S10 shop; the nearest accessibility or gate relation.
- Whether the shops listed are open, still at that spot, or the same entities as S03's (freshness differs by years).
- Station identity at sub-station level (which of the Toei lines or exits).
- Coverage: the 新宿三丁目 list; any other operator's shops in the same corridors.
- Whether Toei or Tokyo publishes shop or exit coordinates elsewhere (none found in the Toei catalogue's 50 datasets by title; descriptions were not read).
