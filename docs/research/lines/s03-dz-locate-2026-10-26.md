## 1. Source and method

Only the Tokyo Metropolitan Government S03 ZIP was fetched:

- SHA256: `fc3466270c08593a300e652c7997021f85151bf0f435e17ee9fcb7935ed4ba31`; 2,317,035 bytes. It matches the brief's required identity.
- CC BY 4.0; this pass uses geometry privately and publishes factual names, levels, devices and derived counts/distances only. Attribution: 出典：東京都都市整備局「新宿駅周辺の施設情報等」; analysis and grouping by the GTEki data lane.

The lead's `s03-dev-ref.py` and `s03-merc-ref.py` were read as references, not edited. Computation used a temporary Python standard-library script, `python3 -I`, inside `orb-test --heavy --memory 1g --cpus 1`. The ZIP, scripts and private output lived under a temporary directory outside this worktree; no raw data or private positions are committed. Python `zipfile` reads the members directly, avoiding the Shift_JIS filename problem with `unzip`.

1. Read `v5_nav.json`. Level properties are triples `[key, value, order]`; take `name` from those triples and `z` from the level record. Every node has exactly one `l[0]`; use that entry's level and `gid`. Match that `gid` to the feature **id** in the corresponding `geojson-level-geom-<floor>.geojson`, not to a feature-array index.
2. Set A: all links for which `dz` (absent means 0) differs from `z(n2) − z(n1)`. Set B: links whose levels differ or whose `dz` is nonzero, unless both endpoint geometries print the same nonempty `facility`. A missing device stays UNKNOWN, even next to a device polygon.
3. Transform both ends privately using the VERIFIED v5_nav frame in [`shinjuku-s03-v0.json`](../../gis/crs/shinjuku-s03-v0.json): `lon = mx / 2^25 * 360 − 180`; `lat = atan(sinh(pi * (1 − 2*my/2^25)))`, converted from radians to degrees. No datum correction or height is derived.
4. Cluster the union A∪B by single linkage: two links join if the shortest of their four endpoint-to-endpoint horizontal distances is **≤30 m**; take the transitive closure. Distances for clustering use the haversine formula with spherical radius 6,371,008.8 m. A cluster is a neighbourhood, not proof that links use one device or one passage.
5. For each end, search only named (`display_name`) geometries on **that end's S03 level**. Distance is to the geometry, not its centroid: zero within a polygon; otherwise the nearest boundary segment, line or point, with polygon holes excluded. This uses a local equirectangular metre conversion about the endpoint and is rounded to 0.1 m. These are approximate source-map distances, not walking distances or a survey.
6. The nearest named feature at every A end is its own device, at **0.0 m**. To give useful context, the endpoint table also lists the nearest named **non-device** geometry. Literal names such as 「A」, 「B」 and 「Unit2F-43」 are printed source labels, not asserted area names or signs that a visitor will find. Where useful for B, an additional nearest named landmark is shown after excluding source `Unit…` placeholders, single-letter/digit labels, devices, ATM/ticket-machine and toilet labels. The primary nearest-context result is retained.
7. Publish only printed names/areas and link-id SHA256 prefixes: `sha256(str(link.id).encode('utf-8'))[:12]`. No coordinates, node IDs, raw link IDs, paths or geometry are published. Cluster labels C01–C18 are local report labels.

## 4. Raised-2F hypothesis: what this source shows

**The requested comparison cannot be made.** There are 40 links between S03 1F and 2F: 31 in one source direction and 9 in the other. Every one is in A. There is no 1F↔2F link with `dz = Δz` to compare by area name. The other consistent cross-level links touching 2F go to 3F (18) or 4F (4); substituting those would change the question.

**There is no one local printed area name across the A clusters.** The nearest non-device context includes 「A」/「B」, 「OdakyuHALCU」, 「KeiodepartmentStore」, 「OdakyuLineSouthExit」, the two JR exit names and unnamed-unit placeholders. C17 has a local 2F landmark 「JREastSouthExit」 (15.7–23.5 m); C18 has 「JRNEWSouthExitMIRAINATOWERExit」 (46.6–60.8 m). Those are two named contexts, not the description of all 42 links. In C01–C08, 2F's nearest non-device name is just 「A」, 86.6–171.3 m away. Calling those clusters 南口 or 新南 from a much more distant named geometry would add an unsupported area assignment.

**Inference only:** `dz = ±3` on all 40 1F↔2F links, and −4 on the two 2F→M1F links, could reflect a different vertical convention attached to these transitions. S03's printed `z` ordering and these `dz` values disagree by two ordinal units. Neither an ordinal difference nor signage measures storey height. The data does **not** establish a deck three physical storeys above 1F, why the values differ, or that only one part of 2F has that condition. Posted floor labels and device types can be fielded; heights and the source's intended `dz` semantics remain GAPs for the data/GIS lane.

**Lead decision (2026-10-26 18:5x JST, data-research-98).** The `dz` mismatch is **source-wide**, not local: every one of S03's 40 1F↔2F links carries `dz` ±3, while the 2F↔3F/4F links agree with `z`. A floor plate read on site cannot explain a `dz` convention, so **Set A gets no field item** (C09's proposed item is withdrawn). Routing should take floor order from each node's level id and the printed `z`, and treat `dz` as an unexplained source attribute; Set A stays a recorded source inconsistency, not a field or routing blocker on its own. Only the three Set B one-end-device links become field items (50–51 below, renumbered).
